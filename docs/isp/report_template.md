# ISP レポートの標準構成（テンプレート）

> 報告のたびに「背景 → 目的 → 問い → プロセス → 結果 → 解釈」を明示し、
> **目的と方法がズレていないかを読者が点検できる**形にするためのテンプレートです。
> 結果だけを報告すると、そもそも何を知りたくて何をしたのかが伝わらず、
> 手段が目的に合っているかを確認できません。

---

## 1. 背景

- 対象疾患・組織・細胞型は何か
- その分野で何が分かっていて、何が分かっていないか
- なぜ計算手法（ISP）を使うのか（実験では何が困難か）

## 2. 目的

**一文で書く。** 「何を明らかにすることか」。
例: 「AD のミクログリアで、削除すると健常側へ戻る遺伝子を順位づけし、介入候補を示す」

## 3. 知りたいこと（検証可能な形に分解）

目的を、判定方法とセットの問いに分解する。

| # | 問い | 判定方法（数値基準） |
|---|---|---|
| Q1 | … | … |
| Q2 | … | … |

**各問いに「どうなれば答えが出たと言えるか」を必ず添える**（[criteria.md](criteria.md) の C1〜C6 を参照）。

## 4. プロセス

1. **データ** — 出典・規模・細胞型・疾患の内訳・なぜそのデータを選んだか
2. **流れ** — 入力作成 → トークン化 → fine-tune → ISP（各段の実装）
3. **実行条件** — トークン長 / 学習細胞数 / 摂動細胞数 / 状態対 / モデル / dtype / チェックポイント
4. **変えた点の履歴** — 途中で条件を変えた場合、**変更理由と影響を必ず併記する**
5. **直した不具合** — 何が起きて、どう直したか

## 5. 結果

- 前提となる性能（分類器の精度など）— **前提が満たされているかを最初に示す**
- 主結果（表・数値）
- **数値だけでなく、その数値が出た理由の実測**（例: 摂動できた細胞数、状態分離の大きさ）

### 評価は「観点 × 基準 × 実測 × 判定」で書く

**評価を書くときは、必ず「何を評価する観点か」と「合格ライン（基準）」を対で示す。**
基準が無い評価は意味を持たない（良し悪しが読者に伝わらない）。

| 観点（何を評価するか） | 基準（合格ライン） | 実測 | 判定 |
|---|---|---|---|
| 信号の大きさ | \|Shift\| > 2.1e-04 | 例: 最大 1.6e-04 | **不合格** |
| 順位の作れやすさ | IQR > 4.2e-04 | 例: 1e-05 | **不合格** |
| 指標の妥当性 | 陰性対照 \|Shift\| < 2.1e-04 | — | 未実施 |
| … | … | … | 合格 / 不合格 / 保留 |

判定は **合格・不合格・保留** のいずれかで明示し、不合格なら理由を書く。

## 6. 解釈

- **現時点で言えること**（断定できる範囲を明示）
- **言えないこと**（データ・指標の限界）
- **ズレの点検** — 「目的・問い」と「方法」が整合しているかを表で確認する

| 目的・問い | 方法が答えられるか | 現状 |
|---|---|---|
| Q1 | … | 未達 / 合格 / 保留 |

- **次の判断ポイント** — どの結果が出たら何をするか（分岐を先に書く）

## 7. 成果物と記録

実行スクリプト・結果・条件の保存場所を一覧にする（再現できるようにするため）。

---

## 付録: 書くときの注意

- **基準を満たしていない結果を「結果」として並べない。** ノイズ域なら「ノイズ域である」と書く
- **変更した条件は履歴として残す。** 良くも悪くも結果の解釈に効く
- **数値には必ず「何を測った値か」を添える**（例: 摂動できた細胞数、状態分離）
- 単位・精度・記号（fp32/bf16、max_ncells など）は初出で定義する
