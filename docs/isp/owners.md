## 3. 担当外の依頼は受信箱に残す（鉄則）

**担当外のページを直したいときは、直接書き換えず、相手の受信箱にメモとして残します。**
commit メッセージに書くだけでは届きません。メッセージは流れて消えるためです。**依頼が確実に届くことが、分担を成立させる条件です。**

| 操作 | できる人 |
|---|---|
| 相手の受信箱に**追記**する | 誰でも可（担当ページの規則の唯一の例外） |
| 受信箱の行を**書き換え・削除**する | その受信箱の持ち主だけ |
| 担当ページを直接編集する | そのページの主担当だけ |

**メモに必ず書く項目**は、対象ページ、直したい点、提案、根拠、状態の5つです。根拠には実測値かファイル名を書きます。

**主担当の義務は2つです。**

1. **作業を始める前に、自分の受信箱（`docs/isp/requests/<自分の呼び名>.md`）を確認します。**
2. **対応したら、その行の状態を「対応済み（コミット番号）」に更新します。** 対応しない場合は、理由を追記します。行は消しません。

受信箱の置き場所と書き方は[受信箱の説明](requests/README.md)にあります。

## 4. 運用ルール（分析）

1. **数値には根拠の種類を添えます。** A は実測、B は他組織や他データからの借用、C は未確立です。合否の線に使えるのは A だけです。
2. **判定の言葉は「合格、不合格、未検証、判定不能」の4語だけを使います。**
3. **基準と目安を区別します。** 目安（IQR、細胞数、状態分離）は合否に使わず、解釈を控える判断に使います。
4. **主張してよい範囲を守ります。** 単一モデルだけの順位は暫定と書き、効果がない場合は「効果なし」と明記します。
5. **必ず併記する条件を書きます。** モデル、組織、時点、摂動できる細胞数、検出率、数値精度です。

## 5. 運用ルール（技術とコード）

1. **編集の前に `git fetch` をします。** 他の執筆者が先に進んでいる場合が多いためです。
2. **主担当以外はそのページを直接書き換えません。** 担当外の依頼は §3 の受信箱に書きます。
3. **push が拒否されたら、取り込んでから push し直します。** 競合が出た場合は[競合の記録](conflicts.md)の方針に従います。
4. **用語や基準を変えるときは、順番を守ります。** 先に[記述ルール](style-guide.md)の該当表を直し、次に[評価基準](criteria.md)の記号と各ページの参照を直し、最後にレポートを再生成します。
5. **commit メッセージには呼び名を書きます。** 例: `docs(isp): AG-MAC の提案を反映`。誰の変更かが後から分かるようにするためです。
6. **レポートはテンプレートのスクリプトで再生成します。** 手作業で数値を転記しません。

## 6. 共有のしかた

このページを編集したら、[索引（README）](README.md)のページ一覧から辿れるようにしておきます。
他の執筆者は `git pull` でこのページを読み、担当と受信箱を確認してください。
担当を変える場合は、変更の理由を添えてこのページを直してください。
