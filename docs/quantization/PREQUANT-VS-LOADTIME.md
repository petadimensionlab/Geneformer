# 調査: 「事前に量子化した重みを保存」と「ロード時に量子化（Geneformer の option）」の違い

**問い**: bitsandbytes などで**あらかじめ量子化した重みを保存しておく**場合と、
**Geneformer の `quantize` オプション（`model_type="Pretrained-Quantized"`）でロード時に量子化する**場合で、
速度や精度に差は出るか？

**結論**:
1. **推論の速度と精度はまったく同じです。** 埋め込みは**ビット単位で一致**しました（差 0.000e+00）。
2. **むしろ、事前に量子化した重みのほうがロード（起動）が遅くなります。**
   104M で 2.0〜2.6倍、316M で **3.1〜6.4倍**遅いという結果でした。
3. 事前量子化の唯一の利点は **ディスク上のサイズ**です（398 MiB → 118.5 MiB / 79.1 MiB）。
4. 副産物として重要な発見があります。**fp32 のチェックポイントはロードが異常に遅く**
   （104M で 3.0秒、316M で 7.3秒）、**何らかの変換（bf16 指定や量子化）を伴うロードにすると
   13〜28倍速くなります**。

---

## 1. 実験方法

スクリプト: `analysis/11_prequant_vs_loadtime.py`（精度・速度の比較）、
`analysis/11b_load_time_bench.py`（ロード時間の反復測定）

- 比較する 2 つの経路
  - **ロード時に量子化（A）**: `BertForMaskedLM.from_pretrained(<fp32 ディレクトリ>,
    quantization_config=BitsAndBytesConfig(...), device_map={"":0})`
    ← Geneformer の `model_type="Pretrained-Quantized"` が内部でやっていること
  - **事前量子化（B）**: 一度量子化して `save_pretrained()` で保存し、
    その保存済みディレクトリを `from_pretrained()` で読む
- 測定条件
  - ロード時間は **5回（316M は3回）反復した中央値**。CUDA コンテキストと
    bitsandbytes のカーネルは事前にウォームアップ済み。全工程
    （`from_pretrained` + デバイスへの転送）を計測。
  - 精度は実データ（AD_blood の 128 セル、マスク 15%）で MLM loss を計算し、
    セル埋め込みを fp32 と比較。
  - 速度は系列長 2048・batch 8 の固定入力。

---

## 2. 結果: 推論の速度と精度は完全に同一

### 104M（AD_blood 128 セル、マスク 15%、系列長 2048・batch 8）

| 方式 | ロード時に量子化 | 事前量子化 | 判定 |
|---|---|---|---|
| int8: tok/s | 59,277 | 58,943 | 同じ（0.994倍） |
| int8: MLM loss | 4.2219 | 4.2219 | **完全一致** |
| int8: 埋め込み | — | — | **ビット単位で一致（差 0）** |
| int8: デバイス上の重み | 118.1 MiB | 118.1 MiB | 同じ |
| nf4: tok/s | 115,118 | 116,097 | 同じ（1.009倍） |
| nf4: MLM loss | 4.4503 | 4.4503 | **完全一致** |
| nf4: 埋め込み | — | — | **ビット単位で一致（差 0）** |

### 316M（AD_blood 64 セル）でも同じ

| 方式 | ロード時に量子化 | 事前量子化 |
|---|---|---|
| int8: tok/s | 26,592 | 26,513（0.997倍） |
| int8: loss | 3.7464 | 3.7464（完全一致） |
| nf4: tok/s | 45,732 | 45,712（1.000倍） |
| nf4: loss | 3.7133 | 3.7133（完全一致） |

**結論（前半）**: 実行時のカーネルと量子化された重みは同じものなので、
**速度も精度も差は出ません。** 事前量子化で得をする点は実行時にはありません。

---

## 3. 結果: ロード時間は「事前量子化」のほうが遅い

ロード時間の中央値（反復測定）。

### 104M

| 方式 | ロード時間 | ディスクサイズ | デバイス上の重み |
|---|---|---|---|
| fp32（量子化なし） | **3.031 秒** | 398.2 MiB | 398.2 MiB |
| bf16（ロード時に変換） | **0.168 秒** | 398.2 MiB | 199.1 MiB |
| int8（ロード時に量子化） | **0.217 秒** | 398.2 MiB | 118.1 MiB |
| nf4（ロード時に量子化） | **0.230 秒** | 398.2 MiB | 77.6 MiB |
| int8（事前量子化） | 0.443 秒（2.0倍遅い） | 118.5 MiB | 118.1 MiB |
| nf4（事前量子化） | 0.590 秒（2.6倍遅い） | 79.1 MiB | 77.6 MiB |
| bf16（事前保存・dtype 未指定） | 0.149 秒 | 199.2 MiB | **398.2 MiB（fp32 に戻る！）** |
| bf16（事前保存・dtype 指定） | 1.431 秒 | 199.2 MiB | 199.1 MiB |

### 316M

| 方式 | ロード時間 | ディスクサイズ | デバイス上の重み |
|---|---|---|---|
| fp32（量子化なし） | **7.251 秒** | 1,206.8 MiB | 1,206.8 MiB |
| bf16（ロード時に変換） | **0.255 秒** | 1,206.8 MiB | 603.4 MiB |
| int8（ロード時に量子化） | **0.384 秒** | 1,206.8 MiB | 330.0 MiB |
| nf4（ロード時に量子化） | **0.398 秒** | 1,206.8 MiB | 193.3 MiB |
| int8（事前量子化） | 2.476 秒（**6.4倍遅い**） | 330.8 MiB | 330.0 MiB |
| nf4（事前量子化） | 1.442 秒（**3.6倍遅い**） | 197.9 MiB | 193.3 MiB |
| bf16（事前保存・dtype 未指定） | 0.275 秒 | 603.5 MiB | **1,206.8 MiB（fp32 に戻る！）** |
| bf16（事前保存・dtype 指定） | 4.668 秒 | 603.5 MiB | 603.4 MiB |

### 解釈

- **量子化済みの重みを読み込むときは、モジュールごとに量子化形式を復元する処理
  （Python レベルの `set_module_quantized_tensor` など）が必要です。**
  いっぽうロード時の量子化は、fp32 の重みを読み込んで GPU 上で一括変換するだけです。
  そのため「事前量子化したほうが速くロードできる」とはならず、逆に遅くなります。
  （この理由の説明は推定です。測定値そのものは反復しても安定しています。）
- モデルが大きいほど差が開きます（104M で 2.0倍 → 316M で 6.4倍）。
- **fp32 のロードが極端に遅い**のも実用的に重要です。104M で 3.0秒、316M で 7.3秒。
  `device_map` を付けても `low_cpu_mem_usage=True` にしても `torch_dtype=torch.float32` を
  明示しても変わりませんでした。**何らかの変換（bf16 指定・量子化）を伴うロードだけが速い**
  という結果です。原因までは特定できていませんが、再現性はあります
  （中央値も最小値も同じ傾向）。
  → **実務的には「ロード時は必ず dtype を指定する（bf16 など）」が正解です。**
- ISP のように遺伝子ごとにプロセスを起動する使い方では、
  この差（316M で 0.4秒 対 2.5秒）が積み上がります。

## 4. 事前量子化を使うべき場面・使わないべき場面

| 目的 | 推奨 | 理由 |
|---|---|---|
| 実行を速くしたい | **事前量子化しない**。ロード時に bf16 指定 or int8 量子化 | 速度は同じで、ロードが遅くなるだけ |
| 起動を速くしたい | **事前量子化しない** | 316M で 0.4秒 対 2.5秒 |
| 保存・配布サイズを小さくしたい | **事前量子化する** | 398 MiB → 118.5 / 79.1 MiB（104M）、1.21 GiB → 331 / 198 MiB（316M） |
| ネットワーク越しに配る、CPU で動かす | **事前量子化する** | 転送量と読み込み量が減る |
| 精度を最優先 | bf16（ロード時に変換でも事前保存でも、dtype を正しく指定すれば同じ） | cos 0.999976 |

**覚え方**: 「保存・配布のために小さくしたい → 事前量子化」、
「実行と起動を速くしたい → 事前量子化しない（ロード時に指定）」。

## 5. つまずいた点（この調査で実際に踏んだもの）

1. **`save_pretrained()` が safetensors の共有メモリで失敗する。**
   `cls.predictions.bias` と `cls.predictions.decoder.bias` が同じ領域を指しているため、
   `RuntimeError: Some tensors share memory ...` で保存できません。
   対策: 保存前に片方を `clone()` して共有を切る（数値は同じ）。
   `analysis/11_prequant_vs_loadtime.py` の `build_prequantized()` に実装済み。
2. **`output_hidden_states=True` で読み込んだモデルは `save_pretrained()` に失敗する。**
   `GenerationConfig.validate()` が
   「`return_dict_in_generate` が未設定なのに `output_hidden_states` が立っている」と判断して
   `ValueError` を出します。対策: 保存用には `output_hidden_states` を付けずに読み込む。
   `analysis/11_prequant_vs_loadtime.py` に実装済み。
3. **bf16 で事前保存したモデルは、そのままでは fp32 として読み込まれる（大きな罠）。**
   保存されるファイルは bf16（199 MiB）なのに、ロード後の重みは fp32（398 MiB）になり、
   **メモリが2倍、推論は5倍遅くなります**（実測 67,338 → 13,428 tok/s）。
   対策: 読み込むときに `torch_dtype=torch.bfloat16` を明示する（`torch_dtype` 引数を省くと
   `config.json` の設定だけでは効きませんでした）。
4. **事前量子化済みディレクトリに `quantization_config` を再度渡しても二重量子化はされません。**
   警告（`Unused kwargs`）が出て、既存の量子化設定がそのまま使われます。無害ですが無意味です。
5. **量子化済みモデルには `.to()` / `.cuda()` を呼べません**（`ValueError`）。
   すでに量子化設定を持つチェックポイントは `device_map` で配置する必要があります。
