# Geneformer V2-316M を 128GB のマシンで動かす計画

対象: `Geneformer-V2-316M`（18層・hidden 1152・語彙 20,275・パラメータ 316.4M）
実行マシン: NVIDIA GB10（メモリ **119.63 GiB**＝公称 128GB、20 cores、aarch64）

---

## 結論（先に要点）

1. **316M は bf16 で動かすのが最適**です。fp32 より **4.9倍速く、メモリは半分**、精度の低下はほぼありません。
2. 実データでの実測では、**316M の bf16 は 104M の fp32 より 1.4倍速い**という結果になりました。
   つまり「大きいモデルにすると遅くなる」という心配は不要で、**速くなりながら精度も上がります**。
3. 316M の重みはすでに取得済みです（`./download.sh --model V2-316M` 実行済み、1.27 GiB）。
4. **int8 / int4 を使う理由はありません**（メモリも速度も bf16 が上。4.の節で詳しく説明します）。
5. ISP（in silico perturbation）を 316M で回すには、**先に 316M のセル分類器の微調整が必要**です。
   既存の分類器はすべて 104M で作られています。
6. **注意点が1つあります**: `analysis/06_finetune.py` の出力フォルダ名にモデル名が入っていないため、
   何もせずに 316M で回すと**既存の 104M の結果を「再利用」して学習がスキップされます**。
   実行前に既存の `runs/` を退避するか、フォルダ名にモデル名を足す小さな修正が必要です（手順 3-1 を参照）。

---

## 1. 316M と 104M の違い

| 項目 | V2-104M | V2-316M |
|---|---|---|
| パラメータ数 | 104.4M | 316.4M |
| 層数 | 12 | 18 |
| hidden サイズ | 768 | 1152 |
| attention ヘッド数 | 12 | 18 |
| 重み（fp32 / bf16 / int8 / int4） | 0.39 / 0.19 / 0.12 / 0.08 GiB | 1.18 / 0.59 / 0.32 / 0.19 GiB |

### 事前学習の質（実測: AD_blood の 256 セル、マスク 15%）

| モデル | MLM loss | マスク予測の正解率 |
|---|---|---|
| 104M | 4.0919 | 0.1135 |
| **316M** | **3.6410** | **0.1368** |

loss が 0.45 低く、正解率は 0.1135 → 0.1368（+21%）です。
**316M に変える価値ははっきりあります。**

## 2. 実測データ

測定スクリプト: `analysis/10_quant_bench.py`、`10c_quant_memscale.py`、`10d_real_workload_mem.py`、`10e_train_mem_probe.py`

### 2.1 推論の速さ（人工データ、batch=8、単位は tokens/秒）

| 系列長 | 104M fp32 | 104M bf16 | 316M fp32 | 316M bf16 |
|---|---|---|---|---|
| 512 | 43,590 | 205,466 | 15,656 | 78,059 |
| 2048 | 35,753 | 174,696 | 13,404 | 64,224 |
| 4096 | 29,672 | 154,269 | 11,407 | 55,407 |

### 2.2 実データでの速さ（AD_blood 512 セル、forward_batch_size=64、最長パディング 3226）

| モデル | 方式 | 512セルの所要時間 | 秒あたりセル数 | ピークメモリ |
|---|---|---|---|---|
| 104M | fp32 | 49.5 秒 | 10.3 | 24.29 GiB |
| 104M | bf16 | 14.1 秒 | 36.3 | 12.16 GiB |
| 316M | fp32 | 130.4 秒 | 3.9 | 34.53 GiB |
| **316M** | **bf16** | **35.8 秒** | **14.3** | **17.28 GiB** |

**316M の bf16 は、104M の fp32 より 1.4倍速く、メモリも 30% 少なく、精度は上です。**
これがこの計画の一番のポイントです。

### 2.3 メモリの伸び方（batch を増やすとどうなるか）

104M、系列長 4096、ピークメモリ:

| batch | fp32 | bf16 | int8 | nf4 |
|---|---|---|---|---|
| 8 | 4.21 GiB | 2.13 GiB | 2.04 GiB | 2.00 GiB |
| 32 | 15.57 | 7.81 | 7.72 | 7.69 |
| 64 | 30.72 | 15.38 | 15.30 | 15.26 |

1 セルあたりの増加量は fp32 で約 0.47 GiB、bf16 / int8 / nf4 で約 0.23 GiB です。
つまり **batch を増やすとメモリは比例して増えますが、速度はほとんど上がりません**
（2.4 節を参照）。batch を増やす意味は「スループット」ではなく
「データローダの待ち時間を減らす」程度です。

### 2.4 大規模にしたときの速度（104M、系列長 2048）

| batch | fp32 | bf16 | int8 | nf4 |
|---|---|---|---|---|
| 8 | 35,753 | 173,872 | 60,190 | 116,906 |
| 128 | 35,458 | 178,157 | 58,236 | 118,756 |
| 256 | 36,055 | 175,173 | 58,042 | 118,829 |

**batch 8 でも batch 256 でも速度はほぼ同じです。** この GPU では batch 8 程度で
すでに演算器を使い切っています。

### 2.5 セル数を増やす・遺伝子数を増やすと int8/int4 が有利になるか → **なりません**

実測した結論は次のとおりです。

- **速度**: 比率は規模によらず一定です。系列長 512〜4096、batch 8〜256、104M / 316M の
  すべてで「bf16 > nf4 > int8」の順番でした。int8 は fp16 で計算し毎回重みを戻すため、
  bf16 より遅いままです。batch を大きくしても逆転しません。
- **メモリ**: 大きい batch ではメモリの大部分が「活性（中間結果）」で、重みの占める割合はわずかです。
  batch 256・系列長 2048 での実測は
  fp32 61.02 GiB / bf16 30.53 / int8 30.45 / nf4 30.41 GiB。
  **bf16 と int4 の差は 0.1 GiB しかありません。**
  つまり int4/int8 のメモリ削減効果は、規模が大きくなるほど相対的に消えていきます。
- 唯一 int8/int4 が有利なのは **ディスク上のファイルサイズ**（重みが 0.4 → 0.1 GiB）と
  CPU 推論です。GPU の速度・メモリでは bf16 に勝てません。

**結論: 規模を大きくしても int4/int8 の利点は出ません。bf16 を使ってください。**
（int8 は fp32 より 1.6〜1.7倍速いので、bf16 が使えない古い GPU では有効な手段です。）

## 3. 実行手順

### 手順 1: 316M を bf16 で読み込んで推論する

```python
import torch
from transformers import BertForMaskedLM
model = BertForMaskedLM.from_pretrained(
    "geneformer_hf/Geneformer-V2-316M",
    output_hidden_states=True,
    torch_dtype=torch.bfloat16,   # ← これだけ
).cuda().eval()
```

`EmbExtractor` を使う場合も、読み込んだモデルを bf16 にするだけで済みます。

### 手順 2: 必要なら 316M のセル分類器を微調整する

ISP は「微調整済みのセル分類器」を使うため、316M で ISP を回すには 316M の分類器が必要です。

```bash
GENEFORMER_DIR=geneformer_hf GENEFORMER_MODEL=Geneformer-V2-316M ADPD_TISSUE=AD_blood \
  .venv/bin/python analysis/06_finetune.py
```

**ここに落とし穴があります。**
`analysis/06_finetune.py` の出力フォルダは
`input/<TISSUE>/runs/<日付>_geneformer_cellClassifier_<PREFIX>_celltype/ksplit1`
という名前で、**モデル名が入っていません**。既存の 104M の結果が同じ場所にあるため、
そのまま実行すると「reusing existing checkpoint」と表示されて
**104M の分類器をそのまま使ってしまいます（学習は実行されません）**。

対策はどちらかです。

- **推奨**: `06_finetune.py` の `RUN_PREFIX` にモデル名を足す
  （例: `RUN_PREFIX = f"{PREFIX}_celltype_{MODEL_NAME}"`）。
  既存の 104M の結果と混ざらなくなります。
- 手早く試す場合: 実行前に `input/<TISSUE>/runs/` を
  `runs-104M-backup/` などへ移動する。

**微調整のメモリは心配いりません**（実測、batch 8・系列長 4096 の 1 ステップ）:

| モデル | fp32 | bf16 | bf16 + 勾配チェックポイント |
|---|---|---|---|
| 104M | 15.40 GiB | 8.03 GiB | **1.82 GiB** |
| 316M | 34.22 GiB | 17.80 GiB | **3.41 GiB** |

316M を fp32 で微調整しても 34 GiB です。119.63 GiB のマシンなら余裕があります。
`06_finetune.py` はすでに `gradient_checkpointing: True` を指定しているので、そのまま安全です。
速さを求めるなら `bf16: True` を training args に追加してください（316M で 4倍速くなります）。

### 手順 3: ISP を 316M で回す

```bash
GENEFORMER_DIR=geneformer_hf GENEFORMER_MODEL=Geneformer-V2-316M ADPD_TISSUE=AD_spleen \
  .venv/bin/python analysis/07_ad_spleen_early_isp.py
```

`analysis/_isp_common.py` が `GENEFORMER_MODEL` を見てモデルを解決し、
微調整済み分類器を `runs/` から探します。手順 2 で 316M の分類器を作ってあれば、
そのまま 316M で ISP が走ります。

### 手順 4: 精度の確認（必須）

316M の結果を、104M の既存結果と比べます。合格ラインは量子化の検証と同じ基準です。

| 指標 | 合格ライン |
|---|---|
| セル埋め込みの一致（同一モデル内の再現性確認） | 変化が 1e-5 未満 |
| セル分類器の macro-F1 | 104M より低下しないこと |
| ISP の `Shift_to_goal_end` の順位 | 104M との順位相関は参考値。**新モデルの結果として妥当か生物学的に確認** |

ここは量子化の話とは違い「モデルを変える」話なので、
**104M と 316M のどちらが正しいかは生物学的な判断**になります。
数値の一致ではなく、結論の妥当性を確認してください。

### 手順 5: 運用パラメータの決め方（119.63 GiB の使い方）

このマシンは GPU メモリと OS のメモリが**同じ 119.63 GiB を共有**しています。
そのため「VRAM をどれだけ使うか」と「ISP のデータをどれだけメモリに置けるか」が
トレードオフになります。目安は次のとおりです。

| 項目 | 316M bf16 での実測値 |
|---|---|
| 重み | 0.59 GiB |
| forward_batch_size=64・最長 3226 トークン | 17.28 GiB |
| forward_batch_size=100・最長 4096 トークン（AD_brain） | 33.67 GiB |
| OS とデスクトップ | 約 3〜5 GiB |

**推奨**: `forward_batch_size=64`（既定）で 17 GiB 程度に収め、
残りの約 100 GiB を ISP のデータセットとページキャッシュに使います。
`forward_batch_size` を 100 に上げても速くならないので、上げる必要はありません。

ISP のメモリは概算で `セル数 × 変異パターン数 × 系列長 × 10 バイト` です。
遺伝子を増やすと変異パターン数が増え、`combos>0` では二項係数で急増します。
既存の運用ルール（`IS_MAX_CELLS` を控えめに、`combos=0`、`nproc=1`）はそのまま守ってください。

## 4. つまずきやすい点

1. **既存の 104M の分類器を誤って再利用する**（手順 2 参照）。いちばん危ない落とし穴です。
2. **`forward_batch_size` を上げても速くならない**。メモリを食うだけです。
3. **量子化モデルに `.to()` / `.half()` を呼ばない**（bf16 は通常のモデルなので問題ありません）。
4. **`datasets==4.0.0` を維持する**（5.x では `perturb_data` が止まります）。
5. 316M は `max_position_embeddings=4096` で 104M と同じです。
   系列長の上限は変わりません。
6. 316M の重みは LFS ポインタのまま置かれていたので、取得済みか必ず確認してください
   （`ls -l geneformer_hf/Geneformer-V2-316M/model.safetensors` が約 1.27 GiB あれば OK）。
