# 検証レポート: Geneformer V2-104M は 48GB の GPU で動くか

対象: `Geneformer-V2-104M`（12層・hidden 768・パラメータ 104.4M）
測定マシン: NVIDIA GB10（メモリ 119.63 GiB・sm_121・aarch64）
想定する実行先: 48GB の GPU（例: RTX 6000 Ada、L40S、A6000 など）

---

## 結論

1. **動きます。しかも量子化は必要ありません。**
   104M は重みが 0.39 GiB（fp32）しかなく、48GB に対してモデル自体は誤差のようなものです。
   律速は「重み」ではなく「活性（中間結果）」で、これはセル数 × トークン数で決まります。
2. **唯一の危険な境界は「fp32 + forward_batch_size=100 + 系列長 4096」の組み合わせ**です。
   実測でピーク **47.77 GiB** でした。48GB の GPU ではここで OOM します。
3. **bf16 に変えるだけでこの問題は解決します**（同じ条件で 23.90 GiB）。
   しかも **4.9倍速く、精度の低下はほぼゼロ**です。
4. int8 量子化も安全に使えます（精度は fp32 比 cos 0.9997）。
   ただし速度は fp32 の 1.7倍にとどまり、**bf16 の半分以下**です。
5. **4bit (nf4) は精度が落ちるので推奨しません**（埋め込み cos 0.981、遺伝子順位 top-100 の一致 87/100）。
6. 微調整まで含めても 48GB で足ります。むしろ 48GB では
   **QLoRA より「bf16 + 勾配チェックポイント」のほうがメモリも速度も有利**です（後述）。

---

## 1. 48GB の内訳をどう考えるか

| 内訳 | 大小 | 決まり方 |
|---|---|---|
| モデルの重み | **小さい**（0.08〜0.39 GiB） | パラメータ数 × データ型のバイト数 |
| 活性（forward の中間結果） | **支配的** | セル数 × パディング後のトークン数 × hidden サイズ |
| 勾配・オプティマイザ状態 | 微調整のときだけ | 学習対象パラメータ数 |
| CUDA の作業領域 | 数百 MB〜 | カーネル依存 |

つまり **48GB を決めるのは「重み」ではなく「1 回の forward に何セル入れるか」**です。
量子化で減らせるのは重み（0.39 → 0.08 GiB）だけで、
活性のデータ型を変える効果（fp32 → fp16 で約半分）のほうが圧倒的に大きい。
これが「bf16 で十分、int4 の出番はない」という結論の理由です。

## 2. 実測データ

### 2.1 系列長 4096（最悪ケース）、人工データ

| batch | fp32 | bf16 | int8 | nf4 |
|---|---|---|---|---|
| 8 | 4.21 GiB | 2.13 GiB | 2.04 GiB | 2.00 GiB |
| 32 | 15.57 | 7.81 | 7.72 | 7.69 |
| 64 | 30.72 | 15.38 | 15.30 | 15.26 |

1 セルあたり: **fp32 約 0.47 GiB / bf16・int8・nf4 約 0.24 GiB**。

### 2.2 実データで測ったピークメモリ

**AD_blood 512 セル、forward_batch_size=64（最長パディング 3226 トークン）**

| 方式 | ピークメモリ |
|---|---|
| fp32 | 24.29 GiB |
| bf16 | 12.16 GiB |
| int8 | 12.08 GiB |
| nf4 | 12.04 GiB |

**AD_brain 200 セル、forward_batch_size=100（最長パディング 4096 トークン）**

| 方式 | ピークメモリ | 48GB で動くか |
|---|---|---|
| fp32 | **47.77 GiB** | **ぎりぎり。ほぼ確実に OOM** |
| bf16 | 23.90 GiB | 余裕あり |

AD_brain は中央値が 2999 トークン、最大 4096 トークンと長い組織です。
**長い組織 + 既定の `forward_batch_size=100` + fp32 が、唯一の危険な組み合わせ**です。
（`forward_batch_size` の既定値は `EmbExtractor` と `InSilicoPerturber` が 100、
`analysis/_isp_common.py` が 64 です。）

### 2.3 各組織の系列長（パディング後の上限を見積もるため）

| 組織 | セル数 | 中央値 | 95%点 | 最大 |
|---|---|---|---|---|
| AD_blood | 48,909 | 1,215 | 2,415 | 3,670 |
| AD_brain | 41,858 | **2,999** | **4,096** | **4,096** |
| AD_liver | 37,453 | 877 | 2,592 | 4,096 |
| AD_smallint | 61,951 | 1,085 | 2,319 | 3,877 |
| AD_spleen | 76,947 | 840 | 1,602 | 2,848 |
| PD_spleen | 83,783 | 925 | 1,922 | 3,587 |

### 2.4 48GB に入る最大の forward_batch_size（最悪 4096 トークン、2 GiB の予備を引いて計算）

| 方式 | 最大のセル数 / forward |
|---|---|
| fp32 | 約 96 セル |
| bf16 | 約 194 セル |
| int8 | 約 194 セル |
| nf4 | 約 194 セル |

**bf16 にすれば 48GB で forward_batch_size を 2 倍にできます**（速度は上がりませんが）。

### 2.5 精度（AD_blood 256 セル、マスク位置 58,855）

| 方式 | MLM loss | マスク正解率 | 埋め込み cos 平均 | cos 最小 | 遺伝子 top-100 一致 |
|---|---|---|---|---|---|
| fp32 | 4.0919 | 0.1135 | 1.000000 | 1.000000 | 100/100 |
| bf16 | 4.0935 | 0.1135 | 0.999976 | 0.999971 | 100/100 |
| **int8** | 4.0823 | 0.1135 | **0.999705** | 0.999635 | 96/100 |
| nf4 | 4.3063 | 0.1053 | 0.981259 | 0.970528 | 87/100 |

**int8 は合格、nf4 は不合格**という判定です。
nf4 は loss の平均は小さい差ですが、遺伝子の順位が入れ替わります（top-100 の一致が 87/100）。
ISP の成果物は遺伝子ランキングなので、この劣化は受け入れられません。

### 2.6 微調整も 48GB で足りるか（batch 8、系列長 4096 の 1 ステップ）

| 方式 | 104M | 316M（参考） |
|---|---|---|
| fp32 | 15.40 GiB | 34.22 GiB |
| bf16 | 8.03 GiB | 17.80 GiB |
| **bf16 + 勾配チェックポイント** | **1.82 GiB** | **3.41 GiB** |
| nf4 + LoRA（QLoRA） | 9.83 GiB | 21.56 GiB |
| nf4 + LoRA + 勾配チェックポイント | 1.95 GiB | 3.39 GiB |

**注目すべき結果: QLoRA（4bit + LoRA）は bf16 の全パラメータ微調整より
メモリを多く使い、遅いです**（104M: 9.83 GiB / 1.60 秒 対 bf16 8.03 GiB / 1.25 秒）。
理由は、bnb の 4bit は「重みを量子化して保存し、計算のたびに戻す」方式で、
戻し用のバッファと計算コストが増えるためです。
4bit のメモリ削減効果（0.39 → 0.08 GiB）は、活性の大きさの前では誤差です。

**48GB で微調整するなら、量子化ではなく「bf16 + 勾配チェックポイント」を選んでください。**
メモリを減らす効果が最も大きいのは勾配チェックポイントです（104M で 8.03 → 1.82 GiB）。

### 2.7 速さ（batch 8、実データ AD_blood 512 セル）

| 方式 | 時間 | 秒あたりセル数 |
|---|---|---|
| fp32 | 49.5 秒 | 10.3 |
| bf16 | **14.1 秒** | **36.3** |
| int8 | 32.6 秒 | 15.7 |
| nf4 | 18.2 秒 | 28.1 |

bf16 が最速です。int8 は fp32 の 1.7倍で、量子化の中では最下位です。

## 3. 推奨する運用設定

### 48GB の GPU で動かす場合

| 項目 | 推奨値 | 理由 |
|---|---|---|
| データ型 | **bf16** | 最速・最小・ほぼ無損失 |
| forward_batch_size | 64（長い組織は 32） | AD_brain（最長 4096 トークン）でも bf16・fbs=100 で 23.9 GiB、fbs=64 なら 15 GiB 程度。速度は上がらないので増やさない |
| int8 を使う場面 | bf16 が使えない環境、または複数ジョブを同居させたいとき | 精度 0.9997 で安全 |
| nf4 を使う場面 | 配布サイズを優先し、精度劣化を許容できるとき | 推論の成果物には非推奨 |
| 微調整 | bf16 + 勾配チェックポイント | QLoRA より速くてメモリも少ない |

### 「48GB で 104M を量子化する意味」のまとめ

- **動かすため**には量子化は不要です（bf16 で足ります）。
- 量子化が意味を持つのは次の場合だけです。
  - bf16 が使えない環境で fp32 の 1.7倍の速度が欲しい → int8
  - 48GB を複数のジョブで分け合いたい → int8（12 GiB 程度に収まる）
  - 配布物のサイズを小さくしたい → int8 / nf4
- **「48GB に載せるため」という理由で 4bit を選ぶ必要はありません。**

## 4. 実行先の GPU に移すときの注意

1. **bitsandbytes がその GPU で動くかを最初に確認してください。**
   このマシン（GB10 / aarch64 / CUDA 13.0）では bitsandbytes 0.50.1 で動作確認済みですが、
   48GB 級のカード（sm_89 / sm_90 など）では別のホイールが必要になることがあります。
   確認方法:
   ```bash
   python -c "import torch, bitsandbytes; print(torch.cuda.get_device_capability(0), bitsandbytes.__version__)"
   ```
2. **速度の順位は GPU によって変わります。**
   今回の「bf16 > nf4 > int8」は GB10 の特性です。
   48GB のカードでは int8 が有利になる可能性があるため、移した先で
   `analysis/10_quant_bench.py` と `analysis/10d_real_workload_mem.py` を再実行してください。
   メモリの見積り（2.1 / 2.2 節）はデータ型ごとの一般的な性質なので、そのまま使えます。
3. **「48GB」は GPU メモリの公称値です。** 実際に使えるのは 44〜46 GiB 程度です
   （ドライバと表示出力が数百 MB〜1 GiB 使います）。
   このレポートの 2.4 節では 2 GiB の予備を引いて計算しています。
4. メモリ不足になったときの対処は、この順番が効果的です。
   1. fp32 → bf16 にする（メモリ半減・速度 5倍）
   2. `forward_batch_size` を半分にする（メモリ半減）
   3. 長い系列を切り詰める（`max_ncells` ではなく系列長を制限する）

## 5. 測定の再現方法

```bash
cd ~/workspace/research/Geneformer

# 速さとピークメモリ（系列長・batch ごと）
.venv/bin/python analysis/10_quant_bench.py
QS_BATCHES=8,32,64 QS_LEN=4096 .venv/bin/python analysis/10c_quant_memscale.py

# 実データでのピークメモリ（組織と forward_batch_size を変えて実行）
ADPD_TISSUE=AD_blood QW_FBS=64  .venv/bin/python analysis/10d_real_workload_mem.py
ADPD_TISSUE=AD_brain QW_FBS=100 .venv/bin/python analysis/10d_real_workload_mem.py

# 精度（MLM loss と埋め込み一致）
.venv/bin/python analysis/10b_quant_accuracy.py

# 微調整 1 ステップのピークメモリ
QT_BATCHES=8 QT_LEN=4096 QT_VARIANTS=bf16,bf16+qc,nf4lora .venv/bin/python analysis/10e_train_mem_probe.py
```

> `10e_train_mem_probe.py` には 1 つ補足があります。
> 4bit の分類器を読み込むとき、transformers 4.46 と bitsandbytes の組み合わせで
> `normal_kernel_cpu not implemented for 'Byte'` というエラーが出ます。
> スクリプト内の `_patch_quantized_init_guard()` がこれを回避しています
> （量子化済みの重みに初期化処理を適用しないようにするだけの小さな修正です）。
> 本番コードで 4bit のセル分類器を作る場合も同じ回避が必要です。
